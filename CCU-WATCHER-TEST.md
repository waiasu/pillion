# CCU resident watcher experiment — test/ccu-watcher-v40

This test is intentionally isolated from the stable v39 VD/CaptureService flow.

- Home: resident Start/Stop immediately disables while a command is pending. A confirmed running observer displays Stop in red. Manual casting Start/Stop is grayed out whenever watcher Start/Stop is pending or watcher is running. Starting the watcher is unavailable while manual casting is running: stop the manual session first. The Reset control is unchanged.
- Foreground observer runs in the private `:ccu_watcher` process, with its own notification channel and Stop action. Android normally instantiates only one instance of a given Service component; duplicate Start also returns without another receiver. `START_STICKY` asks Android to restore it after a system process kill, not after force-stop or reboot.
- **Passive-only detection**: does not call Bluetooth discovery, scan, pair or connect. Android owns auto-connection; the watcher listens for `ACTION_ACL_CONNECTED` / `ACTION_ACL_DISCONNECTED` and adapter OFF/ON events. Candidate identity matches paired Bluetooth devices named `YCCU...` or containing `CCU`.
- Notification shows `CCU探索中` (waiting for an Android connection event, **not actively scanning**), `CCU発見`, `CCU切断・再探索中` (passively waiting for reconnection), or Bluetooth OFF. ACL connection is **not** RFCOMM/NaviLite handshake success. If the watcher starts **after** the CCU is already connected, Android may not send a retrospective ACL_CONNECTED; the notification could remain in waiting state until another connection event. That is deliberately a measurement target.
- This version **does not** establish RFCOMM, start/stop the VD, issue wake/sleep, or act on CCU detection. The Home subtitle labels it a detection-only test. Thus resident Start grays out manual casting but does not yet provide automatic casting; use resident Stop before manual Start.
- For diagnostics: notification state and `logcat -s Pillion-CCU-Watcher`. Export Diagnostics includes `ccu-watcher.log` copied from the independent bounded file in private storage. Log contains event transitions and service start/stop.
- Runtime permissions: BLUETOOTH_CONNECT (Android 12+) and notifications (Android 13+); no BLUETOOTH_SCAN or location requirement for passive detection.
- No edits to `CaptureService`, `DashHelper`, transport, PROMOTE/DEMOTE or the v39 engine.

## 2026-10-22 — six-second trigger flag experiment

- After the **first paired-CCU ACL_CONNECTED** event: mark as a candidate only (`繋げちゃだめ`).
- After a **second ACL_CONNECTED from the same device within six seconds of the previous event**: set internal `mayConnect=true` (`繋げてオッケー`). An intervening ACL_DISCONNECTED is not required because earlier field logs contained repeated connect indications with missing intermediate disconnect broadcasts.
- Every matching ACL_CONNECTED refreshes a six-second inactivity timer. After **six seconds without another connected indication**, clear the flag and the candidate; the next event starts the count from one. A connection gap greater than six seconds, a different CCU, or Bluetooth OFF also resets the count. An ACL_DISCONNECTED is logged and changes the informational status but **does not immediately reset the flag** (brief disconnections are tolerated until timeout).
- Notification **title** shows the derived flag, notification **body** shows the last observed ACL status (connection waiting / connected / disconnected / Bluetooth off). These are *signals*, not RFCOMM/NaviLite availability or a real casting connection. Separate log entries include `ACL_CONNECTED intervalMs=...`, `FLAG_CANDIDATE`, `FLAG_READY`, `FLAG_WINDOW_EXPIRED`, and `FLAG_NOT_READY`.
- An Android handler timer is deliberately lightweight and may execute later than six seconds during deep sleep. All intervals use `SystemClock.elapsedRealtime()`; late callbacks and gaps are checked against monotonic elapsed time. This prototype does not hold a wakelock, schedule alarms or change power management.
- **Observation needed:** if Android maintains one ACL link without repeat notifications, this experimental rule will drop READY after six seconds despite a healthy link. Confirm against XMAX field logs before allowing the flag to initiate any Pillion start/stop. Neither CaptureService nor VD has been modified.

## 2026-10-22 — 30-second indoor one-shot auto-Start test

- Tap **Resident Start** with saved VD mode ON and usual app settings prepared. A temporary 45-second bounded PARTIAL_WAKE_LOCK holds the 30-second delay accurate while the physical display sleeps. Immediately clear Pillion's task from Recents, lock the Pixel, then wait. Do **not** force-stop the app or stop its resident service.
- This one-shot test **ignores actual CCU ACL detection for activation**. Exactly 30 seconds after resident Start, the watcher synthesizes `繋げてオッケー`; actual CCU event logs and the separate six-second ACL flag are still measured but never start casting. No repeating start/stop loop.
- Watcher (`:ccu_watcher`) connects to the existing **127.0.0.1:5555 ADB loopback** using Pillion's normal ADB identity. If it cannot, it logs `TRIAL_FAILED loopback_adb_unavailable` and stops without any normal mirroring fallback. It does not establish RFCOMM or connect to CCU itself.
- If the phone was sleeping, shell sends `input keyevent 224` (WAKEUP), and checks Android `PowerManager.isInteractive`. A one-use random token valid for 90 seconds authorizes `am start -n app.pillion/app.pillion.MainActivity --es ... <token>`; token is not logged. This is intentionally more secure than blindly trusting extras on exported launcher Activity.
- The Activity consumes the token, loads **persisted** Android settings, and reuses the normal VD Start/preflight; **no MediaProjection prompt or fallback** is allowed for this automatic run. On success, it passes a trial ID through the ordinary CaptureService intent. Once `CaptureService` registers the normal screen-off receiver, it broadcasts `TRIAL_CAPTURE_SCREEN_RECEIVER_READY`, which the watcher waits up to 20 seconds for.
- Watcher then issues shell `input keyevent 223` (SLEEP). This deliberately goes through the established `SCREEN_OFF → PROMOTE` pipeline, not a new direct-PROMOTE path. Existing Helper, OCR, AUTO DRIVE, transport, camera and post-PROMOTE recovery stay untouched. The initial wake can illuminate the lock screen briefly; it **does not unlock**.
- The diagnostic export now traces `TRIAL_SCHEDULED`, `TRIAL_FLAG_READY`, `TRIAL_WAKE_REQUEST`, `TRIAL_AM_START_REQUEST`, `TRIAL_SIGNAL`, `TRIAL_SLEEP_REQUEST`, `TRIAL_FAILED`. Stop cancels an outstanding trial. If start or helper preflight fails after wake, the screen may remain on for diagnosis; no blind sleep after a failed start. This is an experiment, not guaranteed background-start behavior on every Android revision.
- This test intentionally does **not** auto-Stop the capture session after the 30-second trigger; use Pillion's own active-stream Stop notification to stop it, or Stop from its screen after ending resident monitoring. Real connection-driven Start/Stop remains unimplemented.
- UI simultaneous-tap recovery: when the Activity rejects a manual Start because the resident watcher won first, the Home's short local tap latch now releases even if the external in-flight flag never became true. Full Android background lifecycle behavior still requires field verification.

## 2026-10-22 — next room-test fixes

- Resident watcher Start is shown only for **NaviLite with VD ON**, and is rejected by MainActivity if VD is disabled. If an observer is already running when VD is switched OFF, its Stop control stays visible until stopped; no stranded foreground service.
- User verified the simultaneous Start-button recovery is working in the earlier build; no further change to capture or button start locks here.
- Earlier room logs showed intermittent `TRIAL_REJECTED invalid_or_expired_token` when the main process was reused. Switched the 90-second, one-shot challenge handover from cross-process cached SharedPreferences to an app-private Android `AtomicFile` read afresh in both processes. Missing/expired tokens still reject auto-start; guessed tokens cannot consume a valid challenge. No change to manual Start, Wake/Sleep order, PROMOTE/DEMOTE, Helper, or actual CCU flag.
